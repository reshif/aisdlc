## Why the thresholds are where they are

Stated before the first run. A person's floor read should feel immediate at 30 items of a project: 250 ms at core,
400 ms at the bff (core's read plus the person's cut and the sandbox slots). Fleet and inbox are smaller reads (400,
500 ms). A work command should go out within three driver polls plus 2 s of work (5 s at the 1 s poll used here).
Postgres at 80 of its default 100 connections, a service at 80% of its `mem_limit`, are where the next step fails.

## Hot spots found and fixed (same harness, same machine, before and after)

The "before" run is `load-m19-before.json`: the factory image built from this branch before the three fixes below (its
`settings.commit` names the checkout the harness ran from, not the image), with the same load tool mounted in
(`LOAD_BUNDLE`). The table is the 4 x 30 run each time.

| measure | before | after |
|---|---|---|
| floor at core, every item in flight, p50 / p95 (ms) | 667 / 1123 | 522 / 915 |
| floor at core while the people act, p50 / p95 (ms) | 2844 / 10157 | 1028 / 3166 |
| floor at the bff while the people act, p50 / p95 (ms) | 2579 / 6708 | 1059 / 2618 |
| floor at core at the end (30 done items each), p50 / p95 (ms) | 1234 / 1531 | 633 / 856 |
| work command latency p50 / p95 (ms) | 2766 / 24842 | 3123 / 18669 |
| 6.0 admission command p50 / p95 (ms) | 7172 / 23721 | 2124 / 18338 |
| admission throughput (Units per minute) | 8.7 | 15.4 |
| items end to end p50 / p95 (s) | 975 / 1205 | 552 / 721 |
| errors seen by the people | 922 | 0 |

1. **The floor's per-item PDP probe** (the suspected one): `item.view_floor` was one full PDP decision per item: the
   bundle verified (Zod parse and a canonical hash of the whole policy bundle), identity's read model caught up (a
   transaction with a row lock on the projection checkpoint, which every other PDP call in the process also takes), the
   principal and each scope's bindings read, and the bootstrap grant looked up, 30 times per read.
   `Pdp.decideEach` (packages/pdp) verifies once and asks the entity source's batch view (`PdpEntityPort.batch`):
   identity folds once and reads the principal and each scope's bindings once, the bootstrap layer reads each
   project's grant once. The answers are decide's, one by one (`packages/pdp/test/decide-each.test.ts` runs the whole
   action x resource matrix).
2. **The bootstrap grant lookup scanned the record**: `liveBootstrap`, asked on every PDP decision about a project
   resource, read `s0.bootstrap_granted` events with no index (a sequential scan of `record.record_event`, growing with
   the record). Migration `0023_bootstrap_lookup.sql`: a partial index.
3. **A work driver pass ran for minutes**: it dispatched up to 20 claims of 20 commands (400 commands, 136 to 234 s per
   pass at 120 items), and a gate decided in the meantime was taken into its item only at the next pass's start, so
   the people kept seeing gates pending they had decided (the 922 errors were mostly their second try, `409
   gate_not_pending`). A pass now dispatches for 10 s at most (`dispatchBudgetMs`); the rest goes on the next pass.

## Still over, and why (not fixed here)

- **The floor read is still 0.9 s at p95** at 30 items with every item waiting at a gate: each read catches up two
  projections (the floor and session activity), works out each waiting gate's feasibility and deciders, folds the
  agent score chips and asks core-worker's `/admission` for the kill banner. The next step is to keep those as
  read models updated by the projection instead of per read; the bff's ETag poll already spares unchanged reads.
- **Work command latency p95 18.7 s**: commands are executed one after another in a pass, and every human decision and
  every ledger entry takes the global ledger append lock and holds it across the Notary's signature (seen in
  `pg_stat_activity`: up to eight sessions waiting on `aisdlc.ledger.append` while the holder was idle in transaction).
  That serialises decisions (the people's 600-odd gate decisions and the driver's ledgered steps) at the Notary's
  round trip. The lock order is a rule of the record (AGENTS.md), so changing it is a design decision, not a load fix.
- Memory and Postgres connections are well inside their limits; no service restarted.
